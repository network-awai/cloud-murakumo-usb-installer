# NixOSとMurakumo Nodeの音声セットアップ設計

AIとの音声会話を主操作にして、言語選択、ネット接続、NixOSのインストール、Murakumo Nodeのアカウント連携を実行する。「接続して」「このSSDに入れて」「アカウントをつないで」と話すと、AIが必要な情報を尋ね、実際の設定処理を呼び、結果を確認して次へ進む。画面は字幕、状態確認、任意の代替操作に使う。基本経路はUSB内で動き、インターネット、スマホ、アカウントなしでもローカルセットアップを完了できる。オンライン連携には登録サービスと本人のPasskeyが必要になる。

この仕様は設計段階。既存のインストール、接続、登録処理を再利用する。音声モデルの実行、USBへの追加、実スマホでの認証はこの設計によって実装済みにはならない。

## 最初に見える画面

提供済みのMurakumoロゴ、NixOSの名前、中央の短い案内、下部の会話字幕を使う。起動ログを主画面に出さない。

起動時は「日本語」「English」「音声で進める」「画面で進める」を表示し、短く「音声セットアップを始める、と話してください」と読み上げる。開始語は端末内だけで検出し、生音声を保存・外部送信しない。開始語またはボタンで音声セッションを開始する。言語と入力方式は声でも変更でき、同じ進行状態を引き継ぐ。セッション終了後は会話用の録音を停止する。

開始後、入力音量と短い試し声を確認する。マイクが複数あれば「USBヘッドセットを使う」と選べる。「少し静かに」「音楽を止めて」「聞き直して」も実行できる。音声ハードウェアがない場合はその事実を表示し、画面操作へ移る。ミュート、字幕、音量、停止は常に表示する。

初回の案内は「NixOSの準備を一緒に進めます。Wi-FiとLANケーブルのどちらを使いますか？ ネットなしでもインストールできます」。一度に質問する内容は一つ。利用者は「Wi-Fi」「あとで」「戻る」「もう一度」「英語にして」などで操作できる。

## 利用者の動線

| 場面 | 音声での案内と操作 | 画面と処理の結果 |
| --- | --- | --- |
| 言語 | 「日本語で」「English」 | 言語を保存し、字幕と音声を同時に切り替える |
| 有線LAN | 「LANを使う」 | 機器、リンク、IP、インターネット、登録窓口を順に確認する。接続済みなら再設定しない |
| Wi-Fi | 「Wi-Fiを使う」「上から二番目」 | SSID一覧を番号付きで表示する。似た名前は候補を絞って確認する |
| Wi-Fiの秘密入力 | 「声でパスワードを入れる」 | 端末内の秘密入力モードに切り替え、一文字ずつの読み方、大文字、記号、訂正を扱う。自由会話LLMと外部送信を切り離し、接続処理へ直接渡す。伏字入力も選べる |
| オフライン | 「ネットはあとで」 | 接続工程を保留して、USB内のインストール資材で進む |
| インストール先 | 「この512GBのSSD」 | 型番、容量、シリアル末尾、既存OSを示す。USB起動媒体を候補から除外する |
| インストールの開始 | 対象を読み返した後「末尾1234のSSDを消去してNixOSをインストールする」 | 対象、既存データの消去、今回の操作に結び付いた明確な音声確認で開始する。長押しは任意の代替。曖昧な「はい」や周囲の会話から消去しない |
| 実行中 | 「何をしている？」「あとどれくらい？」 | 実際の段階と進捗を短く説明する。未計測の残り時間は作らない |
| 再起動 | 「再起動して」 | インストール完了を検証して案内する。USBを抜くタイミングを表示・読み上げ、対象ディスクから起動する |
| 利用方法 | 「この端末だけで使う」「アカウントをつなぐ」 | ローカル完了、オンライン連携のどちらも選べる |
| アカウント連携 | 「スマホで」「このPCで」「Macで」 | QR、音コード、表示URL、端末上ブラウザを選べる。同じ登録フローを使用する |
| 本人確認 | 「認証に進む」 | 明示操作で公式認証画面を開く。利用者がPasskeyの生体認証またはセキュリティキーを操作する |
| 端末の承認 | 認証後「このNodeを、このアカウントに登録して」 | 認証済みセッション内で対象とコードを読み返し、音声確認を受けて既存の承認処理を呼ぶ。API側の認証・対象検証を省略しない |
| 完了 | 自動で次へ | 検証した受領証を保存し、署名付き登録状態を確認して「連携が完了しました」と案内する |

通常の選択、秘密入力、実行確認、やり直し、再起動、端末承認を音声で操作できるようにする。音声の操作確認と本人認証は別の処理である。12桁の初期OSパスワードをこの動線で復活させない。

秘密入力モードでは、ローカルASRと文字入力専用の解析器だけを使う。パスワードを自由会話LLM、遠隔音声モデル、診断ログ、会話履歴に渡さない。大文字小文字や記号を勝手に補正せず、文字数や訂正位置だけを読み返す。接続完了・キャンセル後は音声バッファと入力途中の値を破棄する。周囲に聞かせたくない場合は伏字入力か、検証済みの暗号化Wi-Fi転送を選べる。

PasskeyのOS認証画面、生体認証、セキュリティキーのタッチ、ブラウザのマイク許可は端末の制約に従う。AIから声で開始・誘導できても、現在の汎用ブラウザですべてを無操作で完了できるとは約束しない。対応OSの音声アクセシビリティを使える経路は実機で確認する。音声だけで本人認証を済ませる別方式を加える場合は、既存のPasskey連携とは別の認証方式として検証する。

## スマホなしの完了

三つの完了状態を分ける。

| 状態 | 成立する条件 | 案内 |
| --- | --- | --- |
| ローカルセットアップ完了 | インストールの検証、端末IDとローカル完了情報の保存 | 「この端末の準備ができました。アカウントはあとで連携できます」 |
| アカウント連携完了 | Passkeyによる承認、端末に結び付いた受領証の検証と保存 | 「アカウントとの連携が完了しました」 |
| 今回の起動で登録状態を確認済み | 端末が署名付きオンライン確認に成功 | 「登録状態を確認しました」 |

保存済み受領証があってもオフラインなら「連携情報は保存済み、オンライン確認はあとで」と案内する。登録だけを根拠に、分散推論、報酬、更新の稼働を宣言しない。

スマホがなくても、端末のブラウザ、別のMacやPCのブラウザ、対応するセキュリティキーでPasskey認証へ進める。利用できる認証器がなければローカル完了へ進む。認証方式の追加やアカウントの新規作成は、既存の認証サービスの機能とポリシーに従う。

## 音声モデルの役割

モデルを一つに固定せず、ローカルの基本案内と、条件が整ったときの自然な会話を同じセットアップ制御につなぐ。

| 経路 | 候補と用途 | 採用条件 |
| --- | --- | --- |
| USB内の基本経路 | whisper.cppの多言語baseまたはsmall、同梱小型LLM、ローカルTTS。工程の質問・情報収集・操作提案・結果説明を会話で行う | ネット遮断の実機で日本語・英語の一連の会話と操作が通ること。モデルと実行資材を事前同梱する |
| 動的な日本語読み上げ | VOICEVOX系のローカル合成を評価し、SSD名など変動する情報にも対応 | エンジン、モデル、音声・話者ごとの配布条件を確定し、CPU実測を通すこと |
| Macで自然な会話を評価 | MiniCPM-o 4.5。英語・中国語の全二重会話の比較に使う | Mac向け経路と実機性能を確認。日本語を標準経路として扱う前に別途評価する |
| 接続後の日本語会話 | Qwen3-Omni。自分の対応GPUまたは利用者が選んだMurakumo提供者で動かす | 日本語入出力、遅延、割り込み、字幕、ツール提案の正確さを実測。全二重対応を推定しない |
| 英語の全二重比較 | PersonaPlex、Moshi | 日本語の代替として自動選択しない。対応ランタイムと音声ハードウェアで検証する |

Qwen3-Omniの日本語音声入出力は[公式モデルカード](https://huggingface.co/Qwen/Qwen3-Omni-30B-A3B-Instruct)に記載されている。MiniCPM-o 4.5の公式音声会話は英中で、Mac向け経路を持つ。[公式モデルカード](https://huggingface.co/openbmb/MiniCPM-o-4_5)

PersonaPlexの対象は英語音声で、主な実行環境はNVIDIA GPU/Linux。[公式モデルカード](https://huggingface.co/nvidia/personaplex-7b-v1) MoshiのMac経路は[公式実装](https://github.com/kyutai-labs/moshi)を基準にする。

whisper.cppはCPU実行とMac/Linuxなどをサポートする。[公式実装](https://github.com/ggml-org/whisper.cpp) 日本語TTSの候補は[VOICEVOX Engine](https://github.com/VOICEVOX/voicevox_engine)。以上は候補選定の根拠であり、この端末での性能保証ではない。

初版の必須機能は、自由な言い方を理解して実際の操作を進めるローカルAI会話とする。固定音声だけの案内は障害時の補助であり、AI会話完成の合格条件には数えない。モデルが起動できない場合は画面で継続できるが、音声会話機能は利用不可と明示する。大きなモデルのダウンロードや、登録済みの分散推論経路を、初回Wi-Fi設定の前提にしない。

## 制御の構成

マイク入力を音声認識と対話モデルに渡し、モデルは現在の工程で許された意図だけを提案する。セットアップ制御がその提案を検証し、既存のネット接続、インストール、登録の処理を呼ぶ。実際の結果から次の状態、字幕、読み上げを生成する。

会話モデルにroot権限、任意コマンド、直接のディスク消去、秘密鍵、Wi-Fiパスワード、認証Cookieを渡さない。モデルの生成文にある「成功しました」を完了条件に使わない。SSID、モデル返答、読み取りコードは、命令として実行しない。

共通の状態制御と操作契約はKotoba/CLJKで表し、既存の生成手順でJSへ渡す。既存の`.mjs`バックエンドとGTK画面はアダプターとして残す。音声モデルは公式ランタイムを別プロセスで動かし、障害や遅延をセットアップ処理から切り離す。

| 制御対象 | 再利用する実装 | 追加する契約 |
| --- | --- | --- |
| 状態と案内 | `registration-ui.mjs`のローカル完了、連携、再試行 | 正規化した状態、選択肢、操作中のID、処理結果を音声と画面へ配信 |
| ネット接続 | `network-setup.mjs`のdevices、scan、connect、probe | 接続段階と登録窓口の到達を区別する構造化結果 |
| インストール | 既存の対象ディスク検証とオフライン資材 | シリアルに結び付いた候補、消去前の再検証、進捗、失敗後の回復 |
| ローカル完了 | `local-setup.mjs` | 端末IDに結び付いた永続的な完了結果 |
| 登録 | `account-link.mjs`のstart、poll、status | 同一フローのQR・音・URL表示、期限、キャンセル、受領証の検証結果 |
| 音と画面 | `graphical-ui.js`、`setup-sound.mjs` | 字幕、マイク状態、BGM・読み上げ・FSK音の再生制御 |

操作提案にはsession ID、現在のstate revision、utterance ID、intent、制御側が発行したcandidate IDを持たせる。自由文字列でディスクパスやSSIDを指定させない。同じ提案の再送は一度だけ実行する。別工程や古い音声からの提案は拒否し、現在の選択肢を案内する。

通常操作は会話で得た意図から実行する。消去操作は、候補選択と実行確認を別の発話として扱う。対象シリアル、容量、既存データ消去、状態revision、短い有効期限を一つの操作に固定し、確認を求めている間の新しい発話だけで確定する。対象変更や期限切れでは確認を無効にする。ランダムな確認語を加えても、それを声紋認証や録音対策の保証とは扱わない。インストーラーのディスク検証と一度だけの実行記録は維持する。

認証済みブラウザに音声操作用のアダプターを追加し、登録確認を既存のapprove処理へ渡す。会話モデルに認証Cookieを渡さず、アダプターが現在の認証状態、対象フロー、期限を検証する。Passkeyなしの音声セッションからapproveを呼べる経路は追加しない。

停止は二種類に分ける。「話すのを止めて」は音声だけを停止し、「セットアップを中断して」は中断可能な処理を止める。ディスク書き込みの途中では、安全に止められる段階を画面で示す。中断や音声プロセスの再起動から、消去を再実行しない。

インストール後の再起動では、対象ディスクから起動したことを検証してから案内を再開する。USB側で記録した段階だけを根拠に、インストール済みと判定しない。接続設定、言語、端末ID、保存済み登録、ローカル完了を読み込み、済んだ操作を繰り返さない。

## Passkeyと音コードの受け渡し

音声会話、FSKで送るコード、認証は異なる役割を持つ。FSKの読み取りにLLMを使わず、既存のバージョン・CRC検証を使う。検証済みコードから固定の承認URLを組み立てる。音でCookieや認証情報を送らない。

スマホの音画面では、説明、マイク許可、コード読み取り、承認画面、公式Passkeyログイン、端末承認、完了へ進む。ブラウザのマイク許可と認証画面を開く操作は、利用者のタップなどの明示操作で行う。

公開のブラウザ経路では、音声認識だけをブラウザが要求するユーザー操作として扱わない。許可や認証のOS画面には必要な操作を明示し、対応するネイティブ経路では音声操作の実機検証を行う。認証が戻った後は「この端末を登録して」の会話から承認、Nodeの確認、完了まで自動で進む。

期限切れやキャンセル時は旧コードを無効な表示へ戻し、新しいフローを作ったときだけ新しいQR・音を出す。スマホとNodeの両方で完全な端末IDを確認できるようにする。ログインが済んだだけでは所有権を付与せず、Nodeで受領証を検証して保存するまで完了にしない。

別端末で会話を続ける場合、表示された登録コードだけでローカル管理権限を与えない。将来のMac companion接続は、端末公開鍵に結び付けた別のペアリング、暗号化、明示的な操作権限が必要。mDNSの発見や同じLANであることを信頼の根拠にしない。この接続は基本のオフライン動線には不要とする。

## 声紋認証の研究と採用範囲

音声認識は「何を話したか」、話者照合は「登録された人の声に近いか」を推定する。話者照合の代表的な研究に[ECAPA-TDNN](https://arxiv.org/abs/2005.07143)がある。声の特徴を埋め込みとして比較する技術であり、発話内容の理解やPasskeyの秘密鍵所有とは異なる。

録音再生、音声変換、音声合成、ディープフェイクを使う攻撃と、その検出・耐性も研究されている。[ASVspoof 5の評価論文](https://arxiv.org/abs/2601.03944)は、偽音声検出と攻撃に耐える話者照合を扱う。声が一致した結果だけで、本人がその場で操作を承認したとは判定しない。

[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)は同ガイドラインの認証要件で声による生体照合を使用しないと定めている。これはあらゆる声紋利用を禁止する法律という意味ではないが、MurakumoのPasskeyを声紋で置き換える根拠にはしない。

Murakumoでは声紋を任意の補助機能として研究する。例えば、別の話者が割り込んだ可能性を検知して会話を停止する、本人向けの話し方や言語設定を戻す用途がある。声紋の一致によって認証済みセッションを作ったり、権限を増やしたり、Passkeyの再認証を省略したりしない。声紋を拒否しても音声セットアップを使えるようにする。

登録は利用者が明示的に選び、認証済みの状態で行う。声の特徴は端末内で暗号化して保存し、外部提供者へ配布しない。元音声の保存は別途選択し、テンプレートを削除できるようにする。風邪、加齢、マイク変更、雑音、言語差で照合に失敗してもアカウントをロックしない。

実験では本人の誤拒否、別人の誤受入れ、録音再生・クローン音声の受入れを別々に測る。音声からのランダムな問いへの回答、短い有効期限、端末の署名と組み合わせても、声紋単独の本人認証が成立したとは主張しない。研究結果は音声操作の使いやすさと、アカウント認証の安全性を別々に評価する。

## 音の体験とプライバシー

BGMは起動時に短く、控えめに流す。マイク利用中、秘密入力、Passkey認証、QR・音コード連携の案内中は止める。FSK送信時は読み上げも止め、送信が終わるまで会話の音声操作を停止する。音コードや自分の読み上げを、利用者の操作として受け付けない。

全二重モデルを選ぶ場合も、出力音を参照したエコー対策と割り込み処理を実装する。利用者の割り込みで読み上げを止め、同じ工程の質問に戻る。エコー対策が成立しない実機では、押して話す方式へ切り替える。ストリーミング返答だけを全二重として表示しない。

音声は初期設定では保存しない。ローカル処理を基本にし、外部提供者へ音声を送る前に接続先と共有範囲を表示して選択を受ける。提供者が切り替わるときは黙って送信先を変更しない。秘密入力中は音声と字幕の履歴を作らない。診断記録は工程、結果、所要時間、エラー種別を中心にし、秘密や生音声を含めない。

## 失敗からの継続

| 失敗 | 音声案内と次の操作 |
| --- | --- |
| マイクなし・許可拒否 | 「画面で続けられます」。進行状態を保ったまま切り替える |
| Wi-Fi名の聞き違い | 番号付きの候補を再提示する。接続を勝手に確定しない |
| インターネットなし | オフラインインストールまたはローカル完了へ進む |
| 登録窓口404 | 「登録機能がまだ公開されていません。再インストールは不要です」。接続設定をやり直させない |
| 認証キャンセル | 未連携のまま戻る。新規アカウントや別所有者へ自動で付け替えない |
| 登録期限切れ | 利用者の再試行で新しいコードを表示する |
| 登録解除 | 解除された状態を案内する。自動再登録しない |
| モデル停止・応答遅延 | 固定案内と画面へ切り替える。進行中のインストールを再実行しない |
| 消去後のインストール失敗 | 回復工程へ入る。ディスクの再消去を自動で行わない |

## 実装と受け入れの順序

1. 日本語・英語のローカルASR、小型LLM、TTSと構造化した操作制御を追加する。AIは会話で必要な情報を集め、操作を提案し、制御側が実行する。音声だけで開始、言語変更、音量変更、選択、戻る、再試行ができるようにする。
2. オフラインVMで秘密の音声入力、ネット選択、対象選択、音声による消去確認、インストール、再起動、ローカル完了まで通す。無音、BGM、誤認識、古い発話、二重操作を含める。
3. 実機のUSBマイクまたは内蔵マイク、スピーカー、ヘッドセットで実測し、機器不足時の画面切り替えを確認する。VMの合成音だけでは合格にしない。
4. 本番登録APIと音画面の公開を済ませ、実iPhone・Androidのマイク、QR、Passkey、認証後の音声による端末承認、受領証保存、同じディスクからの再起動確認を通す。OSの本人確認や許可操作が必要な場面を記録する。今回の音声設計は、公開待ちのAPIを公開済みにはしない。
5. 日本語のQwen3-Omniと、MacのMiniCPM-o経路を同じ操作契約で比較する。全二重は実測した経路だけで有効にする。

採用判断用の目標は、割り込みから出力停止までp95で300ms以内、短い操作発話の終了から案内開始までp95で2秒以内とする。未達なら全二重を既定にせず、押して話す方式を維持する。この数値は設計目標であり、現在の実測値ではない。

合格条件は、通常のセットアップ操作で必須のクリック・キー入力ゼロ、コマンド入力ゼロ、初期OSパスワード要求ゼロ、ネット遮断でもAIとの会話でローカル完了、済んだ消去の再実行ゼロ、秘密の自由会話モデル・外部提供者への送信ゼロ、実Passkey承認なしの連携完了判定ゼロである。OS・ブラウザが要求する本人確認や許可は例外として実機結果を示し、全工程が完全ハンズフリーだったと混同しない。音声停止後も画面で継続できること。アカウント連携、推論の稼働、OS更新の正常性は別々の検証結果として表示する。
